# 염주 온라인 서버

Node.js 24 이상에서 `npm install` 후 `npm run dev`로 클라이언트와 서버를 함께 실행합니다. 배포용 빌드는 `npm run build && npm start`입니다. 서버 기본 포트는 3001이며 `PORT`로 바꿀 수 있습니다. 서버는 빌드된 `dist/`도 같은 출처로 제공합니다.

## 현재 구조

- 한 Node.js 프로세스 안에 **테마가 다른 논리 채널 10개**가 있습니다. 각 채널은 최대 108명이며 상태·채팅·채집 재생성·법당 공헌도가 분리됩니다. 물리 서버 10대를 띄우는 구성은 아닙니다.
- WebSocket으로 초당 10회 상태를 보냅니다. 입력 크기는 4KB, 연결당 입력은 초당 45회로 제한하고, 느린 연결은 송신 대기열 256KB에서 닫습니다. 압축은 꺼서 CPU 사용량을 제한합니다.
- 프록시 뒤의 모든 사용자가 같은 소켓 IP로 보이는 점을 고려해 전체 연결과 IP별 연결을 각각 1,200개로 제한합니다. 신규 세션도 소켓 IP당 분당 1,200개까지 발급합니다. 공개 운영의 사용자별 요청 제한은 실제 클라이언트 주소를 안전하게 확인할 수 있는 신뢰된 프록시에서 적용해야 합니다. 요청 헤더만 보고 사용자 IP를 신뢰하지 않습니다.
- 서버가 이동 속도와 월드 경계, 채집 거리/8초 재생성, 절 소요 시간/취소, 아이템 소유권, 장착 가능 수, 무작위 보상, 채널 정원을 검증합니다. 클라이언트가 보상이나 능력치를 직접 결정하지 않습니다.
- `GET /api/session`의 HttpOnly·SameSite 쿠키로 기기를 식별합니다. 임의 256비트 세션 값을 DB에는 SHA-256으로 저장합니다. 로그인이나 계정 이전 기능은 아직 없으며 브라우저 쿠키를 잃으면 기존 소지품에 접근할 수 없습니다.
- 이름·성별(`male`/`female`)·소지품·장비·누적 절 횟수는 SQLite WAL에 저장합니다. 기존 기록에 성별이 없으면 `male`로 시작하며 프로필에서 변경할 수 있습니다. 기본 경로는 `.data/temple.sqlite`이고 `GAME_DB_PATH`로 영속 볼륨 경로를 지정할 수 있습니다. 아이템 변경은 즉시, 이동은 5초 간격과 연결 종료 시 저장합니다.
- 실시간 채널 인원·채집 타이머·공동 108배 진행률·채팅 기록·자리 점유는 메모리에 있으며 서버 재시작 시 초기화됩니다. 채널 이동 시 입구에서 시작합니다.
- `shared/templeLayout.js`에 법당 4채와 수행 자리 108개의 좌표를 정의합니다. `sit { seatId }`는 1.8 단위 이내의 비어 있는 자리만 허용하고 같은 채널의 중복 점유를 막습니다. `stand`·이동·접속 종료·채널 이동 시 자리를 비웁니다. 공개 상태의 `seatId`로 다른 클라이언트도 착석 자세를 표시합니다. 자리 점유는 DB에 저장하지 않습니다.
- 목탁은 클라이언트의 `src/moktakAudio.js`에서 Web Audio로 합성합니다. 서버에는 목탁·오디오 이벤트 처리나 방송이 없으므로 두드리는 사람에게만 소리가 납니다. 착석 상태 동기화와 소리 재생은 별개입니다.
- 자연 채집은 테마 드롭 테이블에서 1개를 보장합니다. 절 완료 시 기본 65% 확률로 1개를 지급하며 드롭률 능력치로 최대 95%까지 높아집니다. 드롭률은 희귀 등급 가중치에도 적용됩니다. 확률과 한도는 `shared/game.js`, `server/index.js`에 있습니다.
- 법당 공동 진행률이 108에 닿으면 최근 10분 동안 기여하고 보상 시점에 해당 법당 범위에 있는 접속자에게 보너스 1개를 지급합니다. 접속만 하거나 다른 채널에 있는 플레이어는 받지 않습니다.

## 운영으로 확장할 때

현재는 개발 가능한 단일 프로세스 MVP입니다. 1,080명 동시 접속 성능이나 여러 서버에 걸친 장애 복구를 보장하지 않습니다. 상태 패킷에는 현재 채널 전체 플레이어와 개인 소지품이 담깁니다. 인원 증가에 앞서 실제 브라우저/네트워크 부하를 측정하고, 주변 플레이어만 보내는 관심 영역, 변경분 패킷, 인벤토리 별도 동기화, 게임 룸 샤딩을 추가해야 합니다.

여러 인스턴스로 확장하려면 채널당 한 인스턴스가 상태를 소유하게 라우팅하고, 공유 계정 DB와 인증을 도입해야 합니다. 여러 프로세스에서 현재 SQLite 파일을 공유하여 같은 채널을 독립 실행하면 정원과 보상 검증이 분산되지 않으므로 지원하지 않습니다. 백업은 SQLite 지원 백업 방식 또는 서버 정상 종료 후 DB/WAL 일관성을 보장해 수행합니다.

리버스 프록시는 WebSocket Upgrade를 전달하고 HTTPS를 종료해야 합니다. 같은 출처로 클라이언트와 `/api`, `/ws`를 제공해야 출처 검증이 통과합니다. HTTPS 운영에서는 `COOKIE_SECURE=true npm start`로 세션 쿠키의 Secure 속성을 활성화합니다. 임의의 `X-Forwarded-*` 헤더를 신뢰하지 않으므로 HTTPS 여부를 헤더로 자동 판정하지 않습니다.

연결당/출처/IP 단위의 기초 제한만 있습니다. 공개 운영 전에는 계정 인증, 신고/차단 및 운영 도구, 프록시 단계의 요청 제한, 세션 만료/삭제 정책, 장애 감시를 갖추어야 합니다.

## 검증

`npm test`는 실제 HTTP와 WebSocket을 열어 채널 격리, 다른 플레이어에게 보이는 이동/채팅, 서버의 거리·속도·타이머·소유권 검증, 공동 보상, 정원 제한, 출처 거부, SQLite 재시작 후 복구를 확인합니다. 자리의 거리·중복 점유·해제·채널 격리, 남녀 성별의 검증·동기화·재시작 복구와 기존 기록 호환도 확인합니다. 소규모 정원 경계 테스트에 더해, 기본 설정에서 실제 소켓 108개가 같은 채널에 동시에 연결되고 109번째 입장이 거절되는지도 확인합니다. 이 연결 한도 검증은 108명이 계속 이동하고 채집하는 성능 부하 시험을 대체하지 않습니다.
